# 요구사항 변경 이력

## 문서 목적

확정 요구사항 변경의 승인·영향·반영을 추적한다.

## 작성 방법

실제 앱 docs/REQUIREMENT_CHANGES.md로 복사한다. {…}를 실제 내용으로 채우고 미결정은 Q ID로 표시한다. 변경 규칙 (`standards/planning/REQUIREMENT_CHANGE_RULES.md`)을 따른다. 변경이 없으면 “현재 변경 요청 없음”으로 두고 아래 양식은 필요할 때 작성한다.
예시는 합성 데이터이며 요구사항으로 자동 채택하지 않는다. 문서 버전·작성자·갱신일을 기록한다.

## 필수 작성 항목

- 변경 ID / 변경 요청일: CHG-{{번호}} / {{날짜}}
- 변경 대상 요구사항 / 기존 버전: {{FR/NFR·버전}}
- 기존 요구사항 / 변경 요구사항: {{전후 내용 또는 정확한 원문 참조}}
- 변경 이유 / 요청자: {{내용}}
- 영향받는 기능 FR / 화면 SCR·흐름 FLOW: {{내용}}
- 영향받는 데이터 / 문서·기획 단계: {{내용}}
- 개발 중인 설계·API·DB·구현·TASK·테스트 영향: {{내용}}
- 비용·일정·위험·대안: {{내용}}
- 변경 상태: PROPOSED / UNDER_REVIEW / APPROVED / REJECTED / APPLIED
- 사용자 승인 여부 / 승인자·날짜·대상 버전·증거: {{내용}}
- 반영 파일·버전·커밋 / 검증 결과 / 남은 작업: {{내용}}
- 재검토·재승인 필요 단계 / 이전 CHG: {{내용}}

## 작성 예시

CHG-001: FR-001의 미래 날짜 허용을 금지로 변경하자는 제안. SCR-001의 날짜 입력, API 검증, TASK-001 테스트에 영향이 있다. UNDER_REVIEW에서는 확정 FR을 바꾸지 않는다. 사용자 승인 후 반영·참조 검증을 마치면 APPLIED로 바꾸고 Phase 3·4·5를 REVIEW로 돌려 재승인받는다.

## 검증 체크리스트

- [ ] 변경 전후·이유·기능·화면·데이터·문서 영향이 있는가
- [ ] 사용자 승인 전 확정 문서가 유지되는가
- [ ] APPLIED에 승인 증거와 반영·검증 기록이 있는가
- [ ] 개발 중인 작업과 재승인 단계도 분석했는가
