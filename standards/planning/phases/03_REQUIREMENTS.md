# Phase 3: Requirements Definition

## 목적과 입력

개발 가능한 상세 요구사항을 정의한다. 현재 PLANNING_STATUS와 사용자 승인된 이전 단계 산출물을 확인한다. 이전 단계 승인이 없으면 단계 전환을 멈추고 필요한 결정을 정리한다.

## 검토 항목

- 기능 요구사항
- 비기능 요구사항
- 입력값 검증
- 정상 처리
- 예외 처리
- 데이터 저장
- 권한 및 보안
- 기능별 완료 조건
- 기능 간 의존성

## 대화 운영

첫 질문 예시: “첫 출시에서 제외하면 핵심 사용 목적을 달성할 수 없는 기능은 무엇인가요?”
한 번에 하나의 주요 의사결정에 집중하고 대안·장단점을 제공한다. 사용자 확정, AI 제안, 미확정을 분리한다. FR별 ID·기능명·설명·우선순위·입력값·처리 규칙·정상 처리·예외 처리·완료 조건·관련 화면·의존 기능을 작성한다. 화면 ID가 아직 없으면 Q로 남기고 Phase 4에서 연결한다. NFR은 측정 방법과 합격 기준을 포함한다.

## 산출물

FUNCTIONAL_REQUIREMENTS.md, NON_FUNCTIONAL_REQUIREMENTS.md, MVP_SCOPE.md. [템플릿 선택표](../PLANNING_WORKFLOW.md)를 사용한다. 문서 변경 후 상태 요약, 미결정, 현재/다음 작업을 갱신한다.

## 완료 조건과 승인

- [ ] 핵심 요구사항이 구체적이다
- [ ] 기능별 완료 조건이 명확하다
- [ ] MVP 범위가 확정되었다
- [ ] 주요 예외 상황이 정의되었다

완료 조건을 확인하면 REVIEW로 둔다. 문서 버전과 결정 사항을 요약해 사용자 승인을 요청하고 명시적 승인 후에만 APPROVED로 기록한다. 미승인이면 다음 단계로 넘어가지 않는다. Phase 5의 마지막 승인 항목도 AI가 체크하지 않는다.
변경으로 완료 조건이 깨지면 영향받는 단계와 문서를 명시하고 재검토한다. [상태 운영 규칙](../PLANNING_STATUS_RULES.md)을 따른다.
