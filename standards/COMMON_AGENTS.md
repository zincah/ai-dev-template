# 공통 개발 지침

- 한국어로 설명하고 코드의 식별자는 프로젝트 관례를 따른다.
- 작업 전 관련 문서와 코드를 읽고 사용자 변경을 보존한다. 기존 파일 덮어쓰기·삭제·대규모 변경 전 충돌을 보고한다.
- 요구사항, 가정, 미결정을 구분한다. 승인된 MVP 범위를 넘는 기능을 임의로 추가하지 않는다.
- 단순한 구조를 우선한다. 상태관리, 아키텍처, DB, 서버 도입은 프로젝트별 결정이며 DECISIONS.md에 이유를 기록한다.
- 기능은 수용 기준으로 검증한다. 실제 실행한 명령과 결과, 미실행 이유를 보고하며 검증하지 않은 성공을 주장하지 않는다.
- 오류·빈 상태·로딩·접근성·개인정보를 설계에 포함한다. 의존성은 기존 버전과 호환성을 확인한다.
- 회사 기밀 코드·데이터·문서·로그·고객정보·자격증명을 개인 기기, 개인 저장소, 개인 ChatGPT/Codex 계정으로 무단 복사하거나 전송하지 않는다.
- 회사 업무는 회사가 승인한 기기·계정·저장소·AI 서비스에서만 수행한다. 재택근무 자체를 반출 승인으로 간주하지 않는다. 승인이 불명확하면 기밀 자료 접근·전송을 멈추고 회사 담당자에게 확인한다.
- 예시는 합성 데이터로 만든다. 토큰, 비밀번호, 서명키, 인증서, 운영 DB 덤프는 소스·문서·프롬프트·로그에 넣지 않는다. .gitignore는 비밀 보호의 충분조건이 아니다.
- 실제 비밀을 발견하면 출력하지 않고 위치와 종류만 알린다. 노출된 비밀은 담당자의 폐기·재발급 절차를 따른다.
- 운영 배포, 스토어 제출, 외부 공유, 유료 리소스 생성, 운영 데이터 변경은 사용자가 명시적으로 승인한 범위에서 수행한다.

## 기획 확장 적용

기획 표준을 사용하는 앱은 standards/planning/PLANNING_WORKFLOW.md와 연결 규칙을 읽는다. 단계 전환·중요 기획 변경·아키텍처 제안의 사용자 승인 경계를 지킨다. Critical이 남은 기획을 완료로 보고하지 않는다. 문서 접근·저장·동기화 여부는 확인 사실만 보고한다. 기존 프로젝트에 새 문서 구조를 강제 이관하지 않는다.
